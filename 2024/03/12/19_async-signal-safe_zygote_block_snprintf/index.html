Hang-zygote 线程死锁卡死白屏问题总结

1.场景

  • 平台：MTK 平台，arm64
  • Android版本：Android U
  • 日志：MTK KE DB 文件、bugreport等
  • 场景：

开关机测试场景：开机后十秒后，自动化测试 apk 触发指令进行重启。
测试步骤：使用公司的自动化测试 app 运行在手机中，测试 app 间隔 15s 执行重启指令重启手机，测试次数 3000 次，时长 3 天。

现象：开关机测试停止，随后手机点击各个应用打不开、白屏、进程无法启动成功，并且机器出现异常，机器保持现场。

2.问题分析

现象分析：该问题从现象上来看会出现手机界面卡住，当尝试打开任意应用时，应用无法打开并且界面白屏，人为进行手动重启后手机能恢复正常。
由于问题发生时，该问题的现场是可以保留的。我们先抓了一份关于打开电话应用的 systrace 日志尝试分析，trace 信息如下：

从trace信息中我们看到应用进程启动过程中bindApplication阶段阻塞，进而导致应用无法正常完成启动。由于所有应用无法启动，怀疑可能是system_server进程创建应用进程出现异常，故抓取bugreport信息。查看system_server中关于创建应用进程的ActivityManager:procStart线程是否有异常。

2.3 调用栈代码排查

经过代码排查，标注的代码流程上有平台添加的功能修改。

功能点：假如第三方跑分软件想要联网，那么就读取线程自身状态，确认是第三方跑分 apk 就直接 return，不让其联网。

平台添加代码解读：
在产品研发阶段，防止手机被安装上性能跑分软件后联网，将手机信息上传到网络上造成信息泄密。

由于添加的代码是在公共库中system/lib64/libnetd_client.so，即每个需要使用网络相关功能包括zygote在内的进程都会调用到添加的接口代码中。
每个进程都会执行一遍 snprintf(path, sizeof(path), "/proc/self/status")，对于 zygote 进程频繁创建进程的场景可能存在异常。

2.5 问题的原因

zygote 主线程创建应用进程流程中等待子线程释放 runtime_shutdown_lock_；子线程持有 runtime_shutdown_lock_ 锁，在创建线程分配内存流程中持有 TSD 锁。这时候突然收到子进程退出的消息，立刻处理子进程退出流程，流程中由于客制化代码 snprintf（字符串存在数组中）也需要内存分配，需要再次持有 TSD 锁。

简化一下流程：
子线程调用 Allocator() 后持有 锁 A，突然收到子进程退出信号，在 SigChldHandler() 中处理信号退出逻辑，然后再次调用到 Allocator() 需要持有 锁 A，结果：此线程阻塞了。

疑点：我开始有些纳闷，为什么线程持锁后，再去获取同一把锁就获取不到呢？

问了一下操作系统相关方面的前辈，表示确实是这样。

并让我了解一下：async-signal-safe 概念。
构想一个线程安全但不可重入的函数：（参考：https://blog.csdn.net/ldong2007/article/details/4271685，英文部分更为有意思）

假设函数 func() 在执行过程中需要访问某个共享资源，因此为了实现线程安全，在使用该资源前加锁，在使用完资源后解锁。
假设该函数在某次执行过程中，在已经获得资源锁之后，有异步信号发生，程序的执行流转交给对应的信号处理函数；再假设在该信号处理函数中也需要调用函数 func()，那么 func() 在这次执行中仍会在访问共享资源前试图获得资源锁，然而我们知道前一个 func() 实例已然获得该锁，因此信号处理函数阻塞——另一方面，信号处理函数结束前被信号中断的线程是无法恢复执行的，当然也没有释放资源的机会，这样就出现了线程和信号处理函数之间的死锁局面。（我们的问题类型就是此种。）

关于 signal-safety - async-signal-safe functions 可以了解下面这篇：

https://man7.org/linux/man-pages/man7/signal-safety.7.html

内容介绍如下：

An async-signal-safe function is one that can be safely called
from within a signal handler. Many functions are not async-
signal-safe. In particular, nonreentrant functions are generally
unsafe to call from a signal handler.

The kinds of issues that render a function unsafe can be quickly
understood when one considers the implementation of the stdio
library, all of whose functions are not async-signal-safe.

When performing buffered I/O on a file, the stdio functions must
maintain a statically allocated data buffer along with associated
counters and indexes (or pointers) that record the amount of data
and the current position in the buffer. Suppose that the main
program is in the middle of a call to a stdio function such as
printf(3) where the buffer and associated variables have been
partially updated. If, at that moment, the program is
interrupted by a signal handler that also calls printf(3), then
the second call to printf(3) will operate on inconsistent data,
with unpredictable results.

To avoid problems with unsafe functions, there are two possible
choices:

(a) Ensure that (1) the signal handler calls only async-signal-
safe functions, and (2) the signal handler itself is
reentrant with respect to global variables in the main
program.

(b) Block signal delivery in the main program when calling
functions that are unsafe or operating on global data that
is also accessed by the signal handler.

在信号处理函数中（signal handler）不能使用非 async-signal-safe 类型的函数，绝大部分函数都不是 async-signal-safe 类型。
例如：我们此题中的 SigChldHandler 子进程退出信号处理函数流程中使用到了 snprintf()，这个方法就不是 async-signal-safe 类型，所以使用后出现了线程内部死锁。

可重入函数：当一个执行流因为异常或者被内核切换而中断正在执行的函数而转为另外一个执行流时，当后者的执行流对同一个函数的操作并不影响前一个执行流恢复后执行函数产生的结果；

给出两种解决方法：

  • 方法一：
    • 确保 1. 信号处理函数调用的方法都是 async-signal-safe 类型函数；
    • 确保 2. 信号处理函数本身是可重入函数，即信号处理函数对于主线程之前的全局变量不能产生影响；
    • （对于本题，信号处理函数已经调用了非 async-signal-safe 类型的函数 snprintf，它本身就已经不是可重入函数了。）
  • 方法二：
    • 主线程调用这些操作全局变量的函数（并且这些函数在信号处理函数中也会被调用）时，将信号屏蔽；
    • （对于本题，应该是不能屏蔽信号的，因为 APP 子进程在不断退出，退出信号无法传到 zygote 的子线程，如果屏蔽掉，那么 APP 子进程会成为僵尸进程。）

4. 问题总结

技巧提炼：

  1. 黑屏、卡死、白屏等问题，必须尽量保存现场；
  2. 根据现象猜测可能哪个模块异常，重点关注系统重要进程例如：SurfaceFlinger、system_server、zygote等；
  3. 能否抓systrace，能抓则在复现场景抓取systrace，以及常规的系统日志（kernel、main、system、events）、bugreport等；
  4. 可以优先使用TOP、PS等命令查看这些进程状态是否存在异常；
  5. 可以向应用进程（包括 system_server）发送 signal 3 导出堆栈信息；对于 native 进程可以发送 signal 35 获取 tombstone 信息，当然也可以使用 debuggerd 命令（和上文中那样，原理也是信号 35 触发）；
  6. 如果确定异常进程，那么可以产生 core 文件，通过 gdb 排查进程的线程情况；
  7. 如果涉及多个模块进程，可能需要产生 KE 或者主动触发 ramdump，通过 crash 等工具进行分析。
