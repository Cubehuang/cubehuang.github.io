system_server binder内存耗尽导致应用crash问题总结

  • Android 版本：Android 16
  • 平台：MTK 平台
  • 问题场景：monkey稳定性测试
  • 问题原因：由于三方应用（com.live.earthmap）频繁与system_server进行大内存Binder消息传输所致。当Settings此时与system_server进行Binder通信时，system_server的binder buffer被耗尽，导致Settings无法访问，从而触发Crash。

1. events 日志线索解读

  • PID：956 - googlequicksearchbox 应用出现了 DeadSystemException。
  • PID：32006 和 3834 - Settings 应用出现了两例DeadObjectException，日志表明在 Settings 与 system_server 的 Binder 交互中，传输一个小的 parcel 时失败，这表明出现了服务端异常，可能是由于服务端 binder buffer 耗尽导致。

问：parcel 要多小才叫“small parcel”？
答：从 android_util_Binder.cpp 代码来看，小于 200KB 的 parcel 为 small parcel。

2. main 日志线索解读

日志逐条解读：

  • E IPCThreadState: Binder transaction failure. id: 253959940, BR_*: 29201, error: -28 (No space left on device)
  • id: 253959940：binder transaction 的 id，一个 binder transaction 只有一个 id，通常我们在其他问题分析过程中可以依靠这个 id 找到 binder 交互对端的信息。
    例如我们可以在 kernel 日志中或者 dump 的 binder 日志中查找这个 id 信息，可以得到以下有用信息：
  • kernel 日志：binder: 32006:5685 transaction call to 1553:0 failed 253959940/29201/-28, size 59848-0 line 3548
  • dump 的 binder 日志：253959940: call from 32006:5685 to 1553:0 context binder node 6873 handle 58 size 59848:0 ret 29201/-28 l=3548

我们从上面的三处 binder 相关的日志来看，它们描述的基本信息都是一致的。

  • BR_*: 29201：这个 29201 是指 binder ioctl 中 BR 操作码，没有什么价值，就是单纯记录 binder 驱动返回到用户态交互的走向。
  • main_log：error: -28 (No space left on device)、kernel_log：/-28 和 binder_log：/-28，这三个信息和 errno-base.h 的 #define ENOSPC 28 /* No space left on device */ 一致，就是指没有空间了，这里指的是 binder buffer 不足了。
  • 两端的交互信息：32006:5685 to 1553:0 就是进程 32006 中线程 5685 向 1553 进程交互，这里的0是什么意思呢？此时由于没有 binder buffer，所以 1553 进程中并没有分配给对应的 binder 线程 提供处理，所以是0。
  • size 59848 则是传输数据量的大小，单位 B，这个数据需要使用 binder buffer 来承载传输，而此时就是由于 1553 中的 binder_buffer 不足以分配 59848B，所以交互失败。
  • line 3548 指的是 binder 驱动中 binder.c 代码的行号，错误是从这里返回去的。

上面的 main 日志差不多就解读完毕，还有一个值得解读的点：

  • pid 32006 com.android.settings sent binder code 140 with...
    这里的 binder code 140，指的是 binder 交互的方法位置。

看一下我下面贴的 crash 日志：getWifiConfigForMatchedNetworkSuggestionsSharedWithUser。

有堆栈的时候我们能一眼看到 binder 交互 的方法是哪一个？如上所示。

如果没有堆栈，我们可能无法知道 binder 交互在哪一个接口，那么我们可以通过这个 binder code 找到哪个方法（不信的话你可以检索一下 getWifiConfigForMatchedNetworkSuggestionsSharedWithUser 这个方法在 aidl 文件中的位置，是不是就是 AIDL 文件中的第 140 个方法）。

值得一提：
以前 Android 老版本中 events日志 中有关键字 binder_sample 打印出 binder 交互接口的耗时信息：
例如：
binder_sample: [android.app.IActivityTaskManager,174,376494,com.XXXX.XXXX,100]，174 表明 xxx 应用 在和 system_server 交互的接口出现了 376494ms 的耗时，接口的位置为 IActivityTaskManager.aidl 中的第 174 个方法。

日志分析完毕，目前问题分析现状如下：

  • Settings 和 system_server 交互过程中，需要申请 system_server 进程中的 59848B 的 binder buffer，申请不到，导致交互失败。
  • 问题：申请的 binder buffer 也不算大呀，binder buffer 已经使用了多少？谁使用多了吗？

3. kernel 日志解读

  • 问题：申请的 binder buffer 也不算大呀，binder buffer 已经使用了多少？谁使用多了吗？

我们能从下面 kernel 日志 得到答案：

日志解析：binder_alloc: allocated: 1030824 (num: 2 largest: 970976), free: 9560 (num: 1 largest: 9560)

  • 已经使用的 1030824B。
  • num：2。binder 驱动中 binder 内存 使用红黑树来管理，已经分配的（已使用）或者可用的（free 的）都使用一个红黑树来管理，这里的 2 其实就是代表 2 个红黑树的节点，代表着已经分配的 binder 内存分别有两个红黑树节点。
  • largest：970976，两个红黑树节点中最大内存的一个为 970976（单位 B）。
  • free: 9560 (num: 1 largest: 9560) 这里也一样，剩余 binder 内存：9560B。

3.1 总的 binder 内存是多少呢？

  • 使用的+剩余的=1030824+9560=1040384B=1016KB=1024KB-8K=1M-2*PAGE_SIZE，这里就是进程映射的专属的一块供 binder 交互的物理内存大小。

为什么是 1M - 8KB？解释如下：

Modify the binder to request 1M - 2 pages instead of 1M. The backing store in the kernel requires a guard page, so 1M allocations fragment memory very badly. Subtracting a couple of pages so that they fit in a power of two allows the kernel to make more efficient use of its virtual address space.

3.2 谁向 system_server 申请那么多内存呢？

通过查找 log，main log 中可以发现如下 log：

  • 13359 进程正在频繁每秒一次申请大的 binder 内存，内存超过 970KB。

当应用进程使用了大的 binder 数据，在 binder 的代码中（frameworks/native/libs/binder/BpBinder.cpp）会进行监控，则会在 main log 中打印日志进行预警。

  • 至此，问题已经较为清晰：13359 进程向 system_server 进行大的 binder 数据传输，内存=970920B。根据对应时间点的 kernel log，可见已分配的 binder 内存 为 1,030,824B（其中包含 13359 进程分配的 970,920B），system_server 剩余可用 binder 内存 仅 9,560B。如果此时有其他进程申请超过 9,560B 的 binder buffer，就会报错。

正如所见，Settings 进程尝试分配 59,848B（大于剩余的 9,560B），因此报错，并导致 crash。

  • 此时我们知道是 13359 进程频繁进行大内存 binder 交互，导致其他应用异常。

问题：如果还想知道 13359 进程（三方应用）频繁调用系统的哪个接口导致异常，该怎么办呢？
